# API and agent access

The application exposes its implemented workforce, school and accounting operations under `/api`. [openapi.json](openapi.json) is its machine-readable inventory; request definitions derive from the same Zod schemas as the service. Staff-directory, clock, workforce-report/overview, linked schedule-request, time-adjustment, retained report-snapshot, import evidence, workbook-conversion and accounting responses have explicit schemas; other response contracts still need expansion. Regenerate with `npx tsx scripts/api-contract.ts` after endpoint changes. The current inventory contains 327 paths and 383 operations, including 41 accounting paths and 47 accounting operations. Implementation inventory is separate from deployment status, which is tracked in STATUS.md.

Browser credentials are private setup → password → expiring server session. Writes require the exact configured Origin, JSON content type, and `X-CSRF-Token` obtained from `/api/me`. A PIN session can only read its identity, read/mutate its own clock, and sign out. No role, organization, employee ID, or timestamp supplied by a caller overrides server identity.

`PATCH /api/me/preferences` saves appearance and dashboard choices for the verified account. Partial updates retain unrelated choices; the strict schema is in `shared/preferences.ts`. Themes are light/dark/system with nine named accent palettes and a custom color. Dashboard order must contain all six known card IDs exactly once, and at least one card must remain visible. Preferences cannot grant a role or bypass data scope. PIN sessions cannot write preferences. Existing light/dark/compact/home clients remain supported.

Owner Settings can create a named bearer token lasting 1–90 days with `reports:read` and/or `staff:read`. Supply `Authorization: Bearer <private token>` over HTTPS. Staff scope permits GET `/api/staff`; report scope permits the documented workforce report/export routes, payroll hours/comparison reads and exports, personal payroll-view listing/resolution, `/api/board`, `/api/workforce/overview`, and scheduled-hours review/export reads. These tokens cannot modify anything or impersonate another employee. Current service checks enforce role and organizational scope in addition to the token scope. Never store tokens in a browser URL, source control, an AI prompt, or a shared report.

Personal payroll views and period comparison contracts are described in [PAYROLL-PREPARATION](PAYROLL-PREPARATION.md). Views store filters only and never retain access after assignments change. Their mutations require a current password session and expected revision; report tokens remain read-only.

Example read (supply the token through your client's secret store):

```http
GET /api/reports?start=2026-09-01&end=2026-09-30&group=week
Authorization: Bearer <secret-store-value>
```

Reports return `workMs`, `breakMs`, `buckets`, `staff`, `rows`, `timezone`, `asOf`, `query`, and a payroll-policy notice. Dates include both selected local calendar days. Row `duration_seconds` is clipped to that range and the report's `asOf`; original segment timestamps remain unchanged. Work and break durations are separate, and neither is a certified wage or payroll calculation. Use `asOf` when explaining a report of open shifts.

Live in `7a2bdc29-ffc9-4f4d-8681-de457ef9df0c`: both direct report routes refresh current account, role, exact unit membership and actual session/scoped bearer proof under locks, then recheck expiry before publication. CSV formatting and its audit share that transaction. Response fields and existing millisecond arithmetic are unchanged. See WORKFORCE-REPORT-AUTHORIZATION.md for evidence and limits.

Clock commands require a fresh UUID `commandId`. Retry an uncertain response with the same ID and identical body; a different payload with that ID is rejected. Supported actions are `clock_in`, `clock_out`, `switch_job`, `start_break`, and `end_break`; only clock-in/job-switch need `jobId`. Switching jobs during a break requires ending the break first.

Imports follow template → preview → human review → apply using the preview ID and source hash. Separate reviewed CSV workflows also cover students, enrollment, class rosters, assignment scores, compensation and financial reports; see their domain contracts. Multiple unit/job UUIDs use pipe characters (`|`) inside their fields. Accounts from an import remain unusable until a manager issues each private setup link. Jev advice receives column headings only and never commits a mapping or import.

## Employee account and job editing

The staff directory includes a canonical revision on every row. Full `PATCH /api/staff/{id}` requires `expectedRevision` along with the employee fields and active state. Stale edits fail with409 instead of replacing newer profile or job assignments; obtain a fresh directory row before retrying. Existing clock-out, account hierarchy and session-revocation rules remain.

`GET /api/staff/{id}/assignments` and `PUT` on the same path provide a separate job/community editor. Administrators may maintain their own and peer administrator assignments as well as lower roles; they cannot change owner/developer assignments. Scoped managers require explicit access to all existing and requested communities of another ordinary employee. The strict write input contains only unitIds, jobIds and expectedRevision. Identical already-applied state returns changed:false without duplicate audit. Adding jobs during an open shift is allowed while preserving its current job/community. Credentials, roles and sessions are not changed. Browser password sessions are required; PIN and bearer access are denied.

## Staff recovery, scheduled starts and workforce bulk entry

`POST /api/staff/{id}/temporary-credentials` lets a current developer, owner or administrator reset a manageable active account with `{commandId,password,pin,requirePasswordChange,requirePinChange,reason}`. Existing hierarchy restrictions apply and self-reset is denied. The two require-change flags default to true and can be chosen independently. Only selected fields must be replaced; a PIN kept for ongoing use must be unique. New employee initialCredentials supports the same options, while omitting it retains private setup. Credential challenges include the selected requirements; completion accepts exactly those replacement fields and preserves the others. Email and temporary password identify the account when a shared temporary PIN cannot. Enabled MFA remains required; old sessions, setup links and credential challenges are revoked. Retry an uncertain request with the same command and unchanged body: a receipt returns current `requiresCredentialChange` without replacing credentials the employee has since chosen. Credentials never appear in responses or audit details.

`GET/PUT /api/staff/{id}/clock-policy` manages the employee-specific `noEarlyClockIn` setting with `expectedVersion`. When enabled, an early ordinary `clock_in` command for an assigned scheduled shift queues a durable intent. It records no worked time until executed. `/api/clock` includes `preclock` policy, pending/latest intent, matching schedules and timezone; old exact command receipts can omit this new field, so refresh the current clock after a legacy replay. `POST /api/clock/preclock/{id}/cancel` accepts `{version,commandId}` under the employee's password or restricted PIN session. A completed intent must be handled through ordinary clock-out; cancelling a pending intent never rewrites worked hours.

`GET /api/workforce/overview?start=YYYY-MM-DD&end=YYYY-MM-DD&unitId=…&userId=…` captures today, the organization-local week and the selected inclusive period together. Exact microsecond strings distinguish work, breaks, scheduled allowance, hours above/below schedule and work outside scheduled intervals. Today/week use the unit filter; the employee filter applies to the selected period. Schedule allowance includes future scheduled shifts in that period. These comparisons are not statutory overtime, leave balances, wages or payroll approval.

`POST /api/workforce/allowance/snapshots` saves an immutable review with `{commandId,query}` using a password session. GET the same route for the latest 100 accessible reviews, or `/{id}` for a captured result. Current and saved exports are `/api/workforce/allowance/export.csv|.xlsx` and `/api/workforce/allowance/snapshots/{id}/export.csv|.xlsx`. Current exports accept the overview query; saved exports use the retained period. These read operations also accept `reports:read` tokens and recheck every captured community. Exports return human-readable two-decimal hours and an `X-STJW-Report-As-Of` header; exact microseconds remain in the JSON review.

Jobs and staff schedules now have actor-owned, create-only imports under `/api/imports/workforce/{kind}`, where `kind` is `jobs` or `schedules`. GET `/template` for blank CSV, POST `/preview` with `{csv}`, GET `/{id}` to reopen review, then POST `/{id}/apply` with `{sourceHash}`. GET the base kind route for the current account's latest 20 accessible previews/receipts. The templates use readable community/job names and employee emails. The server rechecks current source identities, assignments and schedules; changed data requires a fresh preview. The batch either commits completely with a receipt or creates nothing. Exact retries recover that receipt without duplicate creation. See [WORKFORCE-IMPORTS](WORKFORCE-IMPORTS.md) for columns, date offsets, limits and preserved evidence. Excel uses the existing `/api/import-workbooks/*` routes with `kind=jobs|schedules`; conversion alone creates no records. These writes and workbook operations require current password management authority, never bearer tokens.

Errors return `{ "error": "message" }` and sometimes an opaque `incident`. Standard statuses are 400 invalid input, 401 unauthenticated, 403 denied, 404 unavailable, 409 conflict, 413 oversized, 415 non-JSON, 429 throttled, and 503 unavailable optional AI advice. Clients must display failures and refresh state; do not fabricate success after a timeout.

Hosted ChatGPT/Claude OAuth, delegated agent writes, service identities, versioned external contracts and webhooks remain planned. A separate local stdio MCP connector exposes the existing bounded staff/workforce read interface. Browser workflows have domain-specific pagination and reviewed commands; they do not grant agent writes. Future adapters must invoke the same service authorization and audit boundary rather than access the database directly.


## Standalone calendar and messages

`/calendar/events` lists a bounded time window and creates personal, unit or organization events. Recurrence expands into individual occurrences with a common series ID. Updates/cancellations affect one occurrence and require its current version; each change preserves a revision. The original audience is retained to protect history. Personal events are only visible to their creator. Shared unit/organization writes require appropriate managers/administrators. Google sync, resource bookings, invitations and reminders are not implemented.

`/messages` supports own inbox, sent, drafts and archive with 50-row pagination. Drafts are sender-only. Sending revalidates the reviewed version and current permitted active recipients, locks the draft and delivers once under retries. Read/archive state belongs to each recipient. Sent content is immutable. General audit contains metadata, not private content. These messages remain inside the application; external email, family portal delivery, push notifications and attachments are not connected.

Both modules require password sessions. Existing read-only agent tokens have no access to these modules. See the generated OpenAPI inventory for each payload and endpoint.

## Time records and applied corrections

`GET /time-records` lists up to 100 full shifts with date/person filters and offsets; `GET /time-records/{id}` returns the current segments, visible correction history and allowed jobs. A manager needs every unit of the full shift; proposed/historical units are checked separately. `POST /time-corrections` creates an immutable proposal against a source revision and command ID. The same command ID/payload retries safely. Every proposed segment is explicit, ordered, contiguous and nonfuture; code rechecks jobs and overlap under the employee lock. `POST /time-corrections/{id}/review` approves/applies or declines, with current version and review note. The proposer and affected employee cannot review. Approval adds a new revision of segments without editing old segments; reports and exports select the active revision. Proposers may cancel pending corrections. Generic `/requests` decisions remain separate and do not apply a correction. PIN/API tokens cannot use these new routes. The OpenAPI inventory contains 73 paths.

## Accounting books and money workflows

Every `/api/accounting` operation requires a current developer, owner, administrator or finance **password session**. PIN sessions and existing agent bearer tokens cannot use these routes. Current session, role, organization and any enrolled MFA proof are checked transactionally and rechecked before publication. Writes require the configured `Origin`, JSON content type and `X-CSRF-Token` from `/api/me`. Financial roles remain organization-wide; this does not grant school-office or family-record access.

`scripts/api-accounting.ts` generates strict request definitions from the shared validators and maps the actual response objects. `scripts/api-readable-reports.ts` preserves the earlier presentation contracts during full regeneration. Custom Zod refinements also have service-level validation: an OpenAPI shape alone does not establish a balanced journal, valid calendar date, permitted dimension or reviewed reconciliation. Monetary amounts are decimal **strings**, aggregated with integer arithmetic at the configured 0–4 decimal places. UUIDs identify commands and records; they are not report labels or authorization.

| Financial contacts | `GET`/`POST /contacts`; `POST /contacts/{id}` | Explicit vendor, customer, family or donor financial identities with versioned name/details and active status. Contact type stays fixed once documents use it. A family label is not a link to private school-family records. |
| Payables/receivables | `GET`/`POST /documents`; `GET /documents/{id}`; `POST` suffixes `/draft`, `/discard`, `/issue`, `/void`, `/payments`, `/credits`, `/payments/{paymentId}/refund`, `/payments/{paymentId}/void` | Versioned unissued drafts, coded bills/invoices, original-line credits, externally completed payments/refunds, duplicate/reference checks and exact balance limits. AP and AR are independently enabled. Cash-basis issuance/credits do not prematurely recognize unpaid revenue or expense. |
| Aging | `GET /aging?asOf=YYYY-MM-DD&format=json|csv` | Dated balances through the selected date; current, 1–30, 31–60, 61–90, over-90 and separate credit-balance buckets. Names and readable amounts lead the CSV. |
| Banking | `POST /bank-statements/preview`; `GET`/`POST /bank-statements`; `GET /bank-statements/{id}`, `/candidates`; `POST` suffixes `/matches`, `/reconcile`, `/cancel` | Explicit CSV mapping, private reviewed preview, exact signed matching, retained original source and immutable final reconciliation. Cancellation applies only to an open statement and permits corrected reimport. |
| Budgets | `GET`/`POST /budgets`; `POST /budgets/{id}/approve`, `/void`; `GET /budgets/{id}/report?format=json|csv` | Reviewed period/account/fund budgets and actual-minus-budget variance. An unassigned fund means only unassigned entries, not all funds. |
| Payroll accounting | `GET /payroll/options`; `GET`/`POST /payroll`; `POST /payroll/{id}/approve`, `/post`, `/pay`, `/void`; `GET /payroll/{id}/export` | Explicit earnings, rates, deductions and employer costs with captured clock evidence. Approval checks unchanged source and overlapping employee periods. Accrual posts approved payroll before net settlement; cash basis posts at recorded payment. CSV is readable accountant evidence. |
| Statements | `GET /reports?from=...&to=...&format=json|csv|xlsx&view=...` | Posted-journal trial balance, financial position, activities, functional expenses, classified cash movements and ledger detail. Optional community/fund/program/grant/account filters; JSON returns all views, CSV the chosen view, XLSX the full styled packet. |

All payment/refund/payroll-payment endpoints **record externally completed activity**; they do not send money, submit payroll or connect a payment processor. Payroll quantities/rates and accountant-entered deductions are explicit: no statutory withholding, overtime entitlement or organization wage policy is inferred. Tuition/care charges are manually coded document lines; these routes do not infer fee rules or bill from school attendance automatically.

Bank CSV uses ISO dates, signed amounts, a required bank reference and an explicit header mapping. It accepts 1–2,000 lines and at most 1,000,000 characters. Opening balance plus imported movement must equal closing balance. The actor-private preview expires after 24 hours; import requires its reviewed fingerprint. A match accepts either `journalLineId` (null clears) or distinct `journalLineIds` (up to 200; empty clears). The selected posted lines must belong to the same cash account, fall on or before statement end and sum exactly to the bank line. Previously matched/cleared lines cannot be reused.

Final reconciliation requires every bank transaction matched, adjusted ledger balance equal to bank closing, and retained outstanding-line evidence. Subsequent statements follow the preceding reconciled statement's date and closing balance. For the first statement, `openingBalanceReviewed=true` explicitly treats all unmatched pre-statement ledger cash lines as cleared opening evidence; their sum must equal the starting bank balance. This bounded opening workflow does not infer arbitrary reconciling adjustments. `GET /bank-statements/{id}?format=source` returns unchanged original CSV as a text attachment with `X-Source-Hash`; `format=csv` returns the readable current view.

Retry a timed-out command using its original UUID and identical body. A successful retry returns retained evidence rather than creating another entry; another actor or changed body cannot reuse that command. Revision/version conflicts, duplicate documents/references, closed periods, invalid transitions and unbalanced reconciliation return 409. Invalid amounts, dates, coding or payload bounds return 400; missing proof returns 401; denied roles/modes/CSRF or disabled operations modules return 403; missing organizational records return 404. Ledger/planning disabled-module gates can return 409. Transient financial transaction contention returns 503. Re-read current state after conflicts; retain the original command for uncertain retries.

Bounded catalogs are explicit: 2,000 contacts/accounts/dimensions, 500 documents/bank statements/budgets/payroll records, 2,000 aging documents and 10,000 cash-ledger lines per reconciliation. Workspace shows the newest 100 journals with `journalsTruncated`; statement ledger detail shows at most 1,000 lines with `ledgerTruncated`, while its aggregates include the complete matching posted source. Narrow the selected report where possible; a size rejection is not an empty result. Imported financial source reports remain a separate analysis workspace and never post these books automatically.

## Management and operational editing

`scripts/api-editing.ts` extends the generated contract after the domain generators. Request schemas use the actual shared/service validators, or an explicit mapping for the small inline room/review validators. Response schemas include editable catalog versions, financial revisions and history indicators. Run `npx tsx scripts/api-contract.ts` from the application checkout to regenerate all contracts; no new agent-token write permissions are introduced.

| Workflow | Routes under `/api` | Editable fields and retained boundaries |
| --- | --- | --- |
| Jobs | `PATCH /jobs/{id}`; `GET /jobs/{id}/history` | Management role in the permitted community. Edit title, description, active status and, only before references exist, community. Requires `expectedVersion` and reason. Archiving is blocked while a current clock segment uses the job. History returns at most 100 entries plus `truncated` and `communityLocked`. `GET /jobs` includes `description`, `active`, and `version`; POST accepts optional description. |
| Own pending employee requests | `PATCH /requests/{id}`; `POST /requests/{id}/withdraw` | Only the requester may edit or withdraw a pending PTO/general schedule/correction/other request. Edits require current explicit community membership and `expectedVersion`. Withdrawal requires a reason and retains the request as `cancelled`. Reviewed/withdrawn evidence is not overwritten. GET includes `version`; review accepts optional `expectedVersion`, but omission works only at unchanged version 1. Edited requests require the reviewer to acknowledge the current version. |
| Own password | `POST /auth/password` | Strict `{currentPassword,newPassword}` with a different new password of 8–128 characters. Actual current password session and enabled MFA proof are rechecked under the account lock. Returns `{ok:true,csrf}` and rotates the HttpOnly session cookie without extending its expiry. Other sessions, setup links, pending sign-in challenges and API tokens are revoked; existing PIN and enabled authenticator remain. No credential values appear in audit details. |
| School definitions | `PATCH /school/years/{id}`, `/school/terms/{id}`, `/school/courses/{id}` | School administrator or current explicit unit membership plus office grant. All edits require `version` and reason, academic locking, timetable validation and retained school history. Years can be renamed/archived/restored; dates must preserve all child records and cannot shrink after classes/enrollment exist. Locked terms cannot be edited; gradebook-linked term dates stay fixed. Courses can change code/title/description and archive/restore while retaining class references. |
| Timetable rooms | `PATCH /school/timetable/rooms/{id}` | School-office authority, version and reason. Change name/active status while retaining references and validating the resulting timetable. Inactive rooms reject new assignments; an existing meeting may retain its room. GET/POST room responses include `active` and `version`. |
| Financial contacts | `POST /accounting/contacts/{id}` | Financial password role with `commandId`, `expectedRevision`, reason and updated metadata/active status. A used contact cannot change type. Existing document contact snapshots remain unchanged. Responses include `revision` and `active`. |
| Financial document drafts | `POST /accounting/documents/{id}/draft`, `/discard` | Enabled payable/receivable workflow and financial password role. `commandId`, `expectedRevision` and reason are required. Edit unissued drafts without financial events, keeping bill/invoice kind and revalidating active contact, dates, coding and exact amounts. Discard records a zero-amount void event and retained evidence. All document responses, including aging rows, expose `revision`. Issuance may omit `expectedRevision` only for an unchanged revision-1 draft; revised drafts require current revision acknowledgement. |

All new edits are browser-password operations with Origin/CSRF protection. Invalid fields/domain validation return 400, missing/stale sessions 401, denied authority or scope 403, unavailable records 404, and stale or immutable state 409. Password confirmation failure returns 400 while preserving the signed-in session; its 10-attempt/15-minute rate limit returns 429. Financial, school-definition and job lock/serialization contention returns 503 where handled by the service. OpenAPI lists the applicable statuses per route.

Financial edits retain command receipts: retry an uncertain response with the same actor, command UUID and exact body. Job, general-request, school-definition and password edits have no command receipt; refresh and compare the current version/result before another save. After an uncertain password change, refresh and, if prompted, verify sign-in with the new password before retrying. Audit/history evidence stays immutable. Imported financial-report metadata revisions continue through the existing reviewed preview/publish workflow; budget and payroll replacement drafts remain separate records, and payroll recaptures current source evidence.

Calendar occurrence and message-draft editing continue through their existing versioned PATCH routes. Calendar audience changes do not expose retained private history, timetable-derived events are edited through timetable workflows, and sent messages remain delivered evidence.
