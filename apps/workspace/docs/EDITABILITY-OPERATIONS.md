# Operational page editability

Reviewed September 24, 2026 against the current application source. This inventory covers Calendar, staff schedules and schedule requests, Organization, Settings, and internal Messages. Workforce/jobs/general requests and academic/financial records have separate implementation owners in this release.

| Page | Editable parameters and entry point | Review, history, and boundaries |
| --- | --- | --- |
| Calendar | **Edit** beside an editable agenda entry, or open the event and choose **Edit occurrence**. Change its title, description, location, start, or end. | Changes are version checked and retain occurrence history. Existing audience/unit stays fixed so old private history cannot become visible to a new audience; create a separate event to share it elsewhere. Cancellation preserves history. Class events come from **School records → Timetable**, where meetings and conflicts are managed. Personal events remain private to their creator. |
| Schedule / planned staff shifts | Open a scheduled shift to edit its employee/job/time details, or cancel it, with a reason. | Version checks, current assignment validation, explicit daylight-saving offsets, and retained shift history. Planned shifts do not rewrite recorded punches or payroll. A conflicting save retains the draft for comparison against the current shift. |
| Schedule change requests | Edit an unsent proposal; submit a proposed shift change or cancellation. The requester can withdraw a pending request and submit a replacement. | Submitted source/proposal evidence is retained. A different authorized reviewer approves or rejects it, checking the original scheduled version and current assignments. An approved request records the resulting schedule version; later changes belong in a new schedule edit. Requests do not silently change clock history, pay, PTO, or send notifications. |
| Settings → Organization & access → organization units | **Edit unit** changes name, kind, description, or parent after preview/review. Create units and inspect unit history. | Hierarchy/version validation and retained before/after history. Changing a parent never grants inherited access; each subgroup still requires explicit account assignment. Deleting an established unit is not offered because references and history remain in use. |
| Settings → organization branding | Authorized owners/developers edit the branding draft, review it, and publish; historical versions can become a new draft. | Version/history and conflicting-write recovery remain explicit. Branding changes do not rename an account or alter financial/civil identity. |
| Settings → personal appearance | Change and preview personal theme, colors, density, motion, and supported layout preferences. | Save/reset controls and unsaved-change protection are present. Organization branding and personal preferences retain their separate scopes. |
| Settings → Change your password | Confirm the current password, enter and confirm a new **8–128 character** password. | Fresh password session required, including enabled MFA. The current session rotates without extending its deadline; other sessions, setup links, pending sign-in challenges, and API tokens are revoked. Existing PIN and enabled authenticator remain. Passwords, hashes, tokens, and CSRF values never enter audit details. |
| Settings → Quick PIN / authenticator / API tokens | Replace the PIN after current-password confirmation; enroll/manage an authenticator; authorized owners create or revoke supported read-only API tokens. | A token secret cannot be edited or retrieved again; revoke and replace it. MFA and PIN changes use their existing confirmation flows. PIN sessions are restricted to the clock. |
| Settings → organization identity/time zone | Display-only organization identity, time zone, role, and environment. | Role/assignments are administered in staff management. This release does not offer a general organization-name/time-zone editor: time-zone changes affect dated calendars, shifts, and reports and require a defined conversion/review workflow. Branding is independently editable. |
| Messages | Open a draft to change subject, body, and recipients before saving/sending. Read/unread and archive state remain editable per mailbox participant. | Sent message content and recipients are retained as delivered evidence; send a reply/correction instead. Drafts are private to their author. Current recipient access is validated on send, with version checks preventing stale draft sends. Internal messages do not imply email delivery. |

## Improvements in this release

- Calendar agenda entries expose Edit directly. The composer no longer offers the unsupported Classes audience; timetable events retain the correct editing route.
- Metadata-only event changes preserve the original timestamp supplied to the editor, including seconds/fractions and the chosen occurrence of a repeated daylight-saving hour. A changed ambiguous time requires an explicit UTC offset, and nonexistent local times are rejected. Editing only one occurrence does not silently change the recurrence series.
- Calendar drafts participate in the workspace unsaved-change guard and browser unload warning. Modal dismissal asks before discarding a changed draft. While saving, controls and dismissal are disabled; failed validation/version checks retain the draft and display the server error.
- Settings gains self-service password changes with repeat password validation, clear session/token consequences, draft protection, and a transactional authorization/audit boundary. Failed current-password validation retains the signed-in session. Stale sessions require sign-in. An uncertain network result instructs the user to refresh and verify sign-in with the new password before retrying.

## Verification and limits

Focused regressions cover calendar precision, daylight-saving gaps/folds, current password confirmation, eight-character passwords, CSRF and clock/API restrictions, cross-account/org proofs, deactivation/onboarding/MFA/expiry checks, changes occurring during password hashing, concurrent password changes, and rollback when audit insertion fails. Existing calendar service regressions cover retained revisions, stale edits, unit visibility, and private audiences. Browser/mobile verification is recorded with the overall release evidence; this inventory does not itself claim a completed live deployment or browser pass.
